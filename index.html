01 — Why Rocsy exists

Built out of frustration.

Rocsy came from my own frustration trying to get MiniMax H3 running well on a Radeon RX 7900 XTX.

I spent about a month dealing with ROCm setup, compatibility problems, and performance tweaks before I had something I was happy with. Even after that, I was still spending too much time managing ComfyUI and different workloads instead of actually using the machine.

Rocsy is my attempt to make that whole process simpler. It handles setup and optimization, and it includes a GPU queue so image, video, music, voice, and LLM jobs can all share the same hardware without stepping on each other.

The main goal is to make powerful local AI more practical for one person with one machine. You should be able to queue up what you want to run, leave it alone, and let Rocsy handle the messy parts in the background.

03 — The GPU queue

One card. One job at a time.
No collisions.

A dedicated queue service sits in front of every studio. You queue work from anywhere on the site and walk away — Rocsy feeds the GPU in order.

01

FIFO, with priorities

Jobs run in the order you asked for them. Agent work can jump the line; everything else waits its turn.

02

Locked, not crashed

A second studio starting mid-render gets 423 Locked — a clean “wait your turn”, not a VRAM crash.

03

Locks expire

Every lock carries a TTL. If an app crashes without releasing, the queue frees itself instead of wedging the machine.

04

Visible

A /Queue page shows what's running, what's waiting, and what's next. Push notifications land when jobs finish.

04 — How it's built

Containers orchestrate.
The metal computes.

Everything listens on loopback behind the gateway; remote access goes through a Cloudflare Tunnel. GPU-heavy work — ComfyUI, llama.cpp — runs natively on the host where ROCm is fastest.

05 — Run it

Self-host on your own GPU.

Rocsy is a Docker Compose stack. ComfyUI runs natively alongside it; the Trainer is opt-in because its ROCm image is large and training competes for VRAM.

  • One password gates the whole site; sessions ride a signed cookie.
  • Everything on loopback — the only public surface is the gateway, reached through the tunnel.
  • Data stays on the host — outputs, logs and datasets are bind-mounted, not trapped in containers.
setup
# secrets: MASTER_PASSWORD, COOKIE_SECRET,
# QUEUE_INTERNAL_SECRET, LLAMA_API_KEY
$ cp .env.example .env

# bring the stack up
$ docker compose up -d --build

# trainer (opt-in)
$ docker compose --profile trainer up -d --build trainer

# log in, open a studio, queue work
